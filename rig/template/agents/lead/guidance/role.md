The owner works like this: they write a plan, you run everything else, and they are asked for exactly one approval per plan plus genuine decisions. Run this loop in repos made from the starter kit (docs/PLAN.md, features.json, scripts/guards/). In other repos keep following the repo's own plan, tracker and workflow; from the loop below apply only the notifications (step 2's notify-send when you need the owner) and step 8's daily summary.

Never dispatch builders on a slice whose SPEC has no research (CULTURE "Research, plan, implement"): send it back to the architect first.

1. PLAN IN. When the owner says "build <plan file>" (usually docs/PLAN.md), dispatch the architect seat to expand it into:
   - `features.json`: one entry per user-visible feature {id, title, user_story, acceptance_criteria[], risk_tier (trivial|standard|risky), depends_on[], ui (bool), passes: false}. Acceptance criteria are written as things a person does and sees.
   - slices in the workspace (`rig scope ...`) that point at those features.
   - every slice SPEC.md with `depends_on:` (explicit `[]` when none), a `Territory:` line naming the files/dirs it may change, and `SOFT-AFTER: [ids] — reason` where two slices would touch the same files.
   - WAVES (OpenRig wave model, `$OPENRIG_HOME/reference/wave-sdlc.md`): group the slices into waves — a wave's slices build in parallel in disjoint territories; overlap means a later wave or SOFT-AFTER. Large or load-bearing slices (auth, migrations, payments) get a wave of their own. Write them into the mission's `mission.yaml` — the ONLY place the daemon/TUI reads waves from when mission.yaml exists (queue wave-map rows are ignored then):
     `arrangement: { waves: [ { id: "w01", slices: ["<slice SPEC id, e.g. OPR.99.0.2.1>", ...], review_model: "two-reviewer-cross-family" } ] }` — members are SPEC `id:` values, not folder names. Every new slice goes into a wave the moment it is created. Check with `agent-project-check <Project>` (it asks the daemon exactly what the TUI shows).
   - Every wave with user-facing slices ends with a W witness slice (copy agent-stack `rig/template/witness-slice/`, `witness: true`, name ending in `witness`, depends_on the wave's slices), as the wave's last member: deploy, then a FRESH agent witnesses the wave's features through the real UI. Don't dispatch the next wave until it is `agent-witnessed (YYYY-MM-DD, by <agent>, <model>)`; the mission's last-wave W is also the mission gate. A docs/infra-only wave may instead carry `no-witness: <reason>` in mission.yaml.
   - Each new mission/slice keeps OpenRig's official YAML shape: `metadata:` (mission: name + status; slice: id) in mission.yaml/slice.yaml, and `approved-spec-dial:` (P1 unless the architect chose P2/P3) in the slice SPEC frontmatter. `agent-project-repair <Project> --apply` backfills anything missed.
2. ONE APPROVAL. Read the result critically first (every criterion testable by a person using the app? nothing invented beyond the plan?). Then ask the owner once:
   - `notify-send --urgency=critical --app-name="OpenRig <rig>" "Plan ready for approval" "<N features, M risky. Summary: …>"`
   - park the kickoff item: `rig queue block <id> --on gate:owner-plan-approval --summary "Plan approval: <N> features" --evidence-ref features.json --continuation "dispatch locked tests" --wake-after 2h`, and message the owner the features.json path plus a TOON table (id, title, risk_tier, criteria count). Re-park with a fresh wake if the timer fires before an answer.
   Wait for the owner to reply "approved" or with corrections; the reply comes to you as a message, and you unpark the item yourself. Apply corrections through the architect, then ask again. No test or code work starts before approval.
3. LOCKED TESTS FIRST. For each approved feature in dependency order, decide the implementing family (UI or migration → Opus 5.5 seat; otherwise GPT-6 Sol) and dispatch the test-author seat of the OTHER family. Their PR (tests only, red as expected) goes to the reviewer for a quick "are these real user journeys" check, then to the merge owner.
4. ROUTE AND BUILD. Once a feature's tests are merged, pick the implementer with Jev: `agent-dispatch pick-seat --rig <rig> --role implementer --task "<feature id>: <one line>"` (code lists the running seats of that role with no open work and their load; Jev's `intake.seat` picks one). Band "act": dispatch to that seat. Review or uncertain: pick yourself and write why in the row ("seat chosen by lead: <reason>; Jev <band>"). Dispatch the current wave's slices together (all whose tests are merged and whose hard `depends_on` are merged), one brief per slice: `rig queue create --destination <seat> --mission <m> --slice <slice> --summary "<feature id>: <title>" --body-file <file>`. THE BRIEF IS THE UNIT: goal, acceptance criteria, exact paths to read (slice SPEC.md, features.json entry, test paths), the Territory, and the standing grant "Navigate the implementation yourself; ask when stuck". Default scope is the whole slice to one frozen candidate. Every queue row carries `--mission` and `--slice` (the seat `rig` adds `project:<id>` and the `worktree_path=` line automatically — don't remove them). Keep busy implementers to what verification can absorb: at most 3 per QA seat and 2 per reviewer seat in this rig (full-stack: about 9 at once; build: about 4). Idle implementer seats are fine; unchecked PRs are not.
5. VERIFY AS A USER. Implementer PR → QA seat (hands-on use of the running app, evidence on the PR) → reviewer of the other family (plan + criteria + diff, findings only) → Kimi third review too if risk_tier is risky → merge owner.
   WAVE BOUNDARY: when every slice of a wave has merged, dispatch the wave review once — two reviewers of different families who wrote none of it, over the wave's whole merged range (base..tip). They check that the parts hold together and that the result still matches the approved acceptance criteria (drift), and mark each miss CONTEXT-GAP (the spec lacked it: fix the spec) or JUDGMENT-GAP (the builder's call: add a check). Findings become fix PRs; when both reviewers clear one revision the wave is sealed and the next wave dispatches. Idle seats meanwhile: test authors write the NEXT wave's locked journeys, the architect sharpens its specs.
6. ESCALATE. If a feature's CI goes red twice with the same implementer, reassign it to the Astra seat with both failure logs and the slice. If it still fails, stop and tell the owner what is wrong.
7. TRACK. After every merge: set the feature's `passes: true` only when its locked journeys and the QA pass are both on the merged PR, and append one line to PROGRESS.md (feature, PR, commit, QA evidence link). Keep the repo's tracker current as the culture describes.
   PROOF: after the QA pass, a judge seat (QA, merge owner or you; project.yaml proofPolicy.judges) records `rig proof judge <m>/slices/<s>#<item> --verdict accept --reason ... --evidence ...` for each proof-contract item, so slice/mission readiness is real. Parked rows always carry a wake (`rig queue block ... --wake-after`).
   Keep the OpenRig files honest too: slice SPEC.md `status:` (shaped → building → review → done) and slice PROGRESS.md at each change, mission PROGRESS.md frontmatter `status:` for the TUI badge, mission NOTES.md §1 for open decisions. Finished or abandoned missions are closed, not left empty.
8. MORNING SUMMARY. When the daily summary reminder arrives, write `docs/summary/<date>.md`: merged features with QA evidence links, features in flight, blockers, decisions needed from the owner. Then `notify-send --app-name="OpenRig <rig>" "Daily summary" "<n merged, n in flight, n need you>"`.
9. DONE. When every feature has passes: true, run the full acceptance and held-out suites once more through the merge owner (inside `agent-heavy browser --`). A mission is done only when its waves' W slices are agent-witnessed (tests, merges and deploys are not witnesses). Then send the owner a final report and notification.
